# Hindsight 记忆储存

> 原封不动地记录每一句私聊对话，再交给 [Hindsight](https://hindsight.vectorize.io) 沉淀成长期记忆，让 AI 真正记得你。

AstrBot 插件。先把「发生过什么」存下来，再谈记忆——检索、摘要、遗忘都建立在原始记录之上，所以这一层不做任何事后加工，只保证**完整、不重复、可追溯**。

## 适用对象

**适合你，如果**：

- 你在做**一对一的陪伴型 AI**——女友、树洞、私人助理。这类场景里对话是连续的、有情绪的、跨越几个月的，模型上下文装不下，但每句话都值得记住。
- 你自己部署 AstrBot，能顺手起一个 [Hindsight](https://hindsight.vectorize.io) 服务（Docker 一条命令）。
- 你在意「AI 记住的是我说过的话」，而不是「AI 记住的是它自己编的人设」。这个插件的记忆全部来自真实对话。
- 你希望记忆**归你所有**：原始记录躺在本地 SQLite 里，随时能查、能删、能导出，不经过任何第三方。

**不适合你，如果**：

- **群聊场景**。插件只记录私聊（`FRIEND_MESSAGE`），群聊消息一条都不入库——群聊里混入他人记忆是隐私事故，不做比做错好。
- **一个 bot 服务多个互不相识的用户**。每句话按会话分开归档，但抽取出的**事实全部进同一个 Hindsight 记忆库**，召回不做用户隔离。目前适合一对一；服务多人时，A 说的事可能被用来回答 B。真要多用户隔离，得给每个用户单独开 bank，这还没做。
- **想要即时检索**。写入是异步的：提交后入队，服务端抽取事实通常要 80–100 秒。这条链路的取舍是「绝不让记录阻塞回复」，代价是刚说的话不会立刻被记起。
- **没有 Hindsight 服务**。这不是纯本地方案，原始记录本地存，记忆抽取依赖远端（可以是局域网里的另一台机器）。
- **需要跨平台会话打通**（QQ 和微信里是同一个人）。当前会话身份直接取 AstrBot 的 `umo`，不同平台算不同人。

## 它解决什么问题

LLM 没有跨会话的记忆。你把历史全塞进上下文，也是几轮之后就装不下了；摘要又会丢掉细节和情绪。

这个插件的做法是分成两层：

1. **原始层**——每句话逐条落进本地 SQLite。不做摘要、不裁剪、不合并，图片表情也留占位符。这一层是事实的唯一来源，出问题能回溯。
2. **记忆层**——攒够一批就把原始对话投给 Hindsight。它把对话抽成结构化的事实（谁在什么时候做了什么、有什么体验、形成什么观察）并连成图，召回时按语义检索。

于是模型这一轮只需要拿到「和你有关的 5 条记忆」，而不是三个月的聊天记录。

## 工作原理

```
私聊消息 ──▶ 记录（本地 SQLite）──▶ 攒够字数 ──▶ 投递（Hindsight）
                    │                                    │
                    │                              抽取事实、建立图谱
                    │                                    │
                    └────── recall_for() ◀───────────────┘
                                   │
                        下一轮对话注入用户消息（临时内容，不入历史）
```

四个环节各自独立，任一环节挂掉都不影响其余部分：记录失败会告诉用户；投递失败留待下轮重试；召回失败就当这轮没有记忆。

## 功能特性

**记录**

- **原样记录**：用户的每句话、机器人的每次回复，正文原样入库，不做摘要、不裁剪、不合并（去重丢弃的除外，见下条）。
- **按天归档**：同一会话同一天归入一个 `document_id`（`2026-11-09:平台:类型:会话ID`），下游可按天提取事实。
- **内容去重**：对 `document_id + role + 正文` 取 SHA-256 建唯一索引，钩子重复触发、用户中断重发都不会写出重复行。**代价**：同一天同一会话里两段完全相同的正文会被判为重复，只留下第一条——聊两句「嗯」、AI 两次一模一样的回复，后一条不会入库。去重依据目前只有内容，没有消息身份（`message_id`），所以分不清「同一句话被写两次」和「两次说了同一句话」。
- **非文本留痕**：图片、表情、引用、转发以 `[图片]`、`[表情:id]` 等占位符保留，不会因为「没有文字」整条丢失。
- **指令不入库**：`/reset` 这类指令、被唤醒前缀触发的消息不会当成聊天内容。
- **打断过滤**：用户中途打断产生的 `Output stopped.` 占位文本不会当成 AI 的回复存进去。
- **失败可见**：写库失败不静默，用户会收到一条提示；同一故障只提醒一次，恢复后自动复位。
- **零干扰**：只读不写。不拦截、不改写、不影响 AstrBot 的正常回复流程。

**记忆**

- **异步投递**：提交后立即返回，不等服务端抽取。一次同步投入实测要 80 秒以上，等不起。
- **三态追踪**：`待投递 → 已入队 → 已确认`。投出去不等于记住了，得等服务端回话。
- **自动对账**：每轮同步先查上批的状态。成功则落终态，失败先让服务端 retry（`append` 语义下重投会重复追加），屡败才退回重投。
- **幂等提交**：`operation_id` 由本地生成、**提交前先落库**，它就是服务端的幂等键。所以无论是请求超时、进程被卸载、还是凭据写库失败，下一轮都能拿同一个 id 去问服务端要说法：查得到就等它跑完，查不到（404）就说明这批压根没送到，退回重投也不会多出一份内容。
- **三路触发**：攒够 `sync_batch_chars` 字后台自动投、每天 `sync_daily_time` 补投一次、`/hindsight_sync` 随时手动投。
- **召回优先观察**：注入上下文时优先取 `observation` 类型的记忆——它是对多次对话归纳出的结论，比单条事实更接近「这个人是什么样」。
- **说话人消毒**：昵称里的换行和冒号会被清洗。否则一条发言能被劈成两行，甚至伪造出别人的发言人身份。

## 安装

**前置**

- AstrBot v4.x（插件依赖其 `on_llm_request` / `on_llm_response` 钩子）
- 一个可访问的 Hindsight 服务（[部署文档](https://hindsight.vectorize.io)）
- Python 3.10+（由 AstrBot 提供，插件无需额外依赖）

**步骤**

1. 把插件目录放到 `<AstrBot 根目录>/data/plugins/`，**目录名必须是 `astrbot_plugin_hindsight_memory`**（AstrBot 用目录名拼模块路径，从 GitHub 下载的 zip 解压后带 `-main` 后缀，要改掉）。
2. 在 AstrBot 面板里启用插件。
3. 进入插件配置，填 Hindsight 地址和端口（API 用 `8888`，`9999` 是它自己的 Web 控制台）。
4. 私聊机器人发一句话，回面板看日志：出现「已记录 [user] …」说明记录通了。
5. 发 `/hindsight_sync`，出现「✅ 同步完成：N/N 条记录」说明投递通了。
6. 等一两分钟再发一句话，看是否注入记忆（日志里是「已召回记忆 N 条用于本轮对话」）。

## 配置项

| 配置项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `hindsight_host` | string | `localhost` | Hindsight 服务地址 |
| `hindsight_port` | int | `8888` | Hindsight API 端口（不是控制台端口） |
| `hindsight_token` | string | 空 | 可选。服务端未开鉴权就留空，插件不会发 `Authorization` 头 |
| `hindsight_bank_id` | string | `01a1c652-f619-77c9-87ab-ad9d71a5c910` | 写入与召回共用的记忆库。服务端已有数据时必须填一致，否则会对着空库召回 |
| `sync_batch_chars` | int | `5000` | 单批字符上限，同时也是「攒够多少字提前投递」的阈值 |
| `sync_daily_time` | string | `00:05` | 每日补投时刻，`HH:MM`，按本机时区 |
| `recall_memory_quantity` | int | `5` | 每轮注入的记忆条数 |
| `user_nickname` | string | 空 | 记忆里「用户」的称呼。平台给的是哈希 id 时填这个 |
| `llm_nickname` | string | 空 | 记忆里「AI」的称呼。留空则用人格名 |

`user_nickname` 和 `llm_nickname` 值得单独说一句：Hindsight 靠 `名字 (时间): 内容` 这样的文本识别说话人。传 `10001` 这类数字串，它抽出来的实体名会退化成 `user`，「她喜欢看海」这种人格化事实就建立不起来。昵称取不到时，填一个固定称呼比什么都不填强得多。

## 指令

| 指令 | 说明 |
| --- | --- |
| `/hindsight_sync` | 立刻把本地待投递的记录提交给 Hindsight，回复投递结果 |

## 数据存储

**原始记录**：`<AstrBot 根目录>/data/plugin_data/astrbot_plugin_hindsight_memory/db/sqlite/raw_message.db`

| 字段 | 说明 |
| --- | --- |
| `id` | 自增主键 |
| `record_date` | 记录日期 `YYYY-MM-DD`（按本机时区，不是 UTC） |
| `document_id` | `日期:平台:消息类型:会话ID`，一天一个文档 |
| `sender_id` / `sender_name` | 发送者 ID 与昵称 |
| `persona_id` | 当轮生效的人格 |
| `role` | `user` 或 `llm` |
| `raw_message` | 正文，非文本以占位符表示 |
| `message_sent_time` | 消息发生时刻，ISO 8601 带时区 |
| `content_hash` | 去重指纹：`document_id + role + 正文` 的 SHA-256，唯一索引。不含时间与人格，也不含消息 ID |
| `flushed` | `0` 待投递 / `1` 已入队 / `2` 已确认 |

`db/sqlite/` 下还有 `raw_message.db-wal` 和 `-shm`。SQLite 开了 WAL 模式，**备份时三个文件要一起拷**，或者先执行 `PRAGMA wal_checkpoint(TRUNCATE)`。

**记忆**：存在 Hindsight 服务端（默认 PostgreSQL + pgvector），不在本机。

## 故障排查

| 现象 | 排查方向 |
| --- | --- |
| 日志完全没有「已记录」 | 是不是群聊？插件只记私聊 |
| 「⚠️ 本条对话记录保存失败」 | `raw_message.db` 被占用或磁盘满；看日志里的具体异常 |
| `/hindsight_sync` 报「请求超时」 | 服务端在处理，但耗时超过 `RETAIN_TIMEOUT`；异步提交正常不会卡这么久，检查网络 |
| `/hindsight_sync` 报「HTTP 404」 | `hindsight_bank_id` 填错，或服务端从没建过这个库（插件会自动建） |
| 「本轮没有命中记忆」一直出现 | 记录还没投递成功，或 bank 是空的；先跑一次 `/hindsight_sync` |
| 召回到的记忆是英文的 | 服务端抽取模型的倾向问题，与插件无关，详见 [docs/hindsight-api.md](docs/hindsight-api.md) |
| 记忆里的名字是 `user` | 配置 `user_nickname`，或确认平台能提供真实昵称 |

## 隐私与数据安全

这个插件处理的是最私密的那类数据，所以直说三点：

- **原始对话只存在你本机**的 SQLite 文件里，不经过任何第三方服务。它跟 AstrBot 的配置文件、人格设定一样，属于该备份的东西。
- **抽取事实时会发到 Hindsight 服务**。如果那个服务是远程的、或用了第三方 LLM，得你自己确认它可信——插件不替你做这个判断。
- **卸载插件不会删除** `data/plugin_data/astrbot_plugin_hindsight_memory/`。要彻底清除，手动删掉该目录，以及 Hindsight 服务端对应的 bank。
